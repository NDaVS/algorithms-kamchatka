# Зимний мониторинг Камчатки

Самостоятельный сервис для проверки гипотезы «камера помогает раньше определить, какой участок проверить». Прогноз предупреждает заранее, наблюдения по камерам формируют оперативные сигналы, утренняя сводка собирает события и решения. Пользователь отмечает своё решение в карточке сигнала.

Автор интеграции — [Eazyan](https://github.com/Eazyan).

## Быстрый запуск

Нужны запущенный Docker Engine с Compose, Python 3 и Bash. На чистой копии из папки компонента выполните:

```bash
./bootstrap.sh
```

Команда создаёт локальный `.env`, генерирует пароль PostgreSQL, подготавливает четыре синтетических кадра и запускает приложение. Откройте [локальный дашборд](http://127.0.0.1:8080). На чистом компьютере для сборки образов нужен доступ к реестрам. В демо приложение использует локальные кадры и контрольный прогноз. Ожидаемый результат — один срочный сигнал и одно предупреждение.

Для запуска со свежими кадрами на чистой копии используйте `./bootstrap.sh --preview`. Адрес общего GPU API и контракт `scene_v2` уже записаны в `.env.example`. Существующий `.env` сохраняется, поэтому для переключения ранее запущенного демо измените в нём `MONITOR_MODE=preview` и снова запустите `./bootstrap.sh`. Для реального прогноза заполните `OPENWEATHER_KEY`. Для проверки своей серии подготовьте её через `fixtures/prepare_demo.py`.

## Компоненты

| Компонент | Обязанность |
| --- | --- |
| React + TypeScript | Сигналы, кадры, прогноз, карта подтверждённых точек, решения и журнал доставки |
| FastAPI | Версионированный API, проверка токенов, разграничение прав, аудит и выдача медиа |
| Обработчик | Сбор камер HLS/JPEG, вызов Weather VLM, правила сигналов, OpenWeather, SMTP и сводки |
| PostgreSQL | Миграции, наблюдения, эпизоды, прогнозы, решения и долговечные очереди |
| Медиа | Локальный том или S3-совместимое хранилище |
| Weather VLM | Отдельный GPU-сервис. Контракт `/v1/scene` описывает наблюдаемые признаки |

Сильный снегопад со сниженной видимостью на дорожной камере становится срочным сигналом после двух свежих подтверждений. Для обычного снегопада требуются три. Снимки с тротуара или погодного ракурса не поднимают приоритет дорожного участка. Зафиксированная оператором реакция хранится независимо от физического окончания эпизода.

Состояние события и запись доставки создаются в одной транзакции. Повторный запуск не создаёт второе письмо с тем же ключом. При неопределённом результате SMTP письмо остаётся в журнале со статусом неопределённой доставки. Время хранится в UTC, сводка и показ в интерфейсе используют `Asia/Kamchatka`.

## Закрытый пилот

1. Разверните GPU API с `POST /v1/scene` на выделенном endpoint и сравните ответы на четырёх контрольных кадрах. `POST /v1/snow` сохраняет поддержку прежних полей `image` и `images`. Файлы и инструкция GPU-сервиса находятся в [cameras](cameras) и [документации Ubuntu](docs/WEATHER_VLM_UBUNTU.md). Согласуйте переключение с владельцем действующего API.
2. Определите реальные ракурсы и их дорожную привязку в `monitoring/cameras.json`. Стартовая конфигурация включает Завойко как дорожную камеру и Чехова как погодную до проверки ракурса. Согласованные координаты задаются как `[долгота, широта]`. Для карты по умолчанию используются публичные плитки OSM при наличии подтверждённых точек.
3. Перед API устройте HTTPS-вход с OIDC и проксированием Bearer-токена в `Authorization` для HTML, API и кадров. Для браузерного входа шлюз должен обрабатывать OIDC-сессию и сам выставлять заголовок после проверки. API проверяет RS256, issuer, audience и срок токена; роли сопоставляются с настроенными значениями `sub`. Хостовый порт Compose привязан к loopback.
4. Задайте `MONITOR_MODE=live`, HTTPS-адреса в `PUBLIC_URL` и `MODEL_URL`, параметры OIDC в файле окружения. Настройте ключ OpenWeather и TLS SMTP. Сначала проверьте канал на тестовом адресате, затем задайте согласованный список `MAIL_TO`. При пустом списке сообщения сохраняются в журнале.
5. Перед открытием пилота проверьте доступность и свежесть камер, результат инференса, получение трёх видов письма, сохранение очереди после перезапуска и восстановление копии PostgreSQL и медиа. Настройте ротацию медиа и журналов по условиям пилота. В Compose база и медиа находятся на одном сервере, резервные копии должны храниться отдельно. Для закрытого пилота один экземпляр обработчика владеет планировщиком через advisory lock.

Адаптер использует [OpenWeather One Call 3.0](https://openweathermap.org/api/one-call-3). Стартовый порог вероятности задаётся через `SNOW_PROBABILITY`. Сводка выпускается в 07:00 по Камчатке и повторно не создаётся для той же даты.

## Проверка и воспроизведение

```bash
npm --prefix web ci
npm --prefix web run build
python3 -m venv .venv
.venv/bin/pip install -r requirements-test.txt
TEST_DATABASE_URL='postgresql://user:password@127.0.0.1:5432/test' .venv/bin/python -m pytest -q
```

Используйте временную базу для интеграционных тестов. Тесты создают отдельные запуски, проверяют PostgreSQL, HTTP, матрицу решений, повтор запроса и SMTP на локальном приёмнике.

В режиме `replay` загрузите манифест с временами и наблюдениями командой `python -m monitoring.replay /path/to/manifest.json --id scenario-a`. Затем откройте дашборд с `?run=scenario-a`. Структура манифеста видна в `runtime/demo/manifest.json` после подготовки демо. Каждое наблюдение применяется к правилам в порядке времени съёмки.

## Реальные данные и демо на одном Mac

Для локального просмотра реальных данных установите `MONITOR_MODE=preview`. Основная страница показывает реальные камеры, а [демо](http://127.0.0.1:8080/demo) использует свой набор записей и медиа. Локальный API Compose доступен по loopback. В этом режиме сообщения попадают в журнал. Для рабочего доступа с рассылкой используется отдельный режим `live` с HTTPS и OIDC.

В примере окружения указан общий адрес Weather VLM v2. Для собственного экземпляра поменяйте `MODEL_URL`. Подробные признаки поступают из `/v2/scene`. При неполном результате `/v1/snow` может уточнить признак падающего снега. Для V2 в карточке «Видимость по кадру» показывает качество обзора, если отдельной оценки видимости в ответе нет. Заключение формируется по-русски из валидированных полей. Укажите `OPENWEATHER_KEY` для получения реального прогноза.

PostgreSQL хранит времена, события, решения и очередь. Для фотографий можно использовать локальный том или закрытый S3. В локальном Compose доступно объектное хранилище SeaweedFS. Задайте `S3_BUCKET=kamchatka-frames`, `S3_ENDPOINT=http://object-store:8333`, случайные `AWS_ACCESS_KEY_ID` и `AWS_SECRET_ACCESS_KEY` в `.env`. S3 доступен только в сети Compose. Демо продолжает читать файлы из своего тома.

```bash
docker compose -f compose.yaml -f compose.s3.yaml build api
docker compose -f compose.yaml -f compose.s3.yaml up -d --no-build
```

Регулярно копируйте PostgreSQL и том объектного хранилища. Копия базы содержит ссылки на кадры и восстанавливается вместе с самими объектами. Для рабочего развёртывания можно указать внешний S3-совместимый адрес и выдать приложению ключ с доступом к выделенному бакету.

## Прогноз и работа с сигналами

OpenWeather One Call используется первым. При отказе в доступе сервис запрашивает стандартный прогноз на пять суток с шагом три часа. Карточки прогноза отображают фактический горизонт. Предупреждение формируется отдельно от наблюдений камер и следует настройке `SNOW_PROBABILITY`.

Очередь проверки показывает по одному свежему открытому сигналу на дорожную камеру. Выше стоят срочные сигналы, затем более важные участки и более свежие подтверждения. Вес участка `road_priority` и его объяснение `road_priority_reason` задаются в `monitoring/cameras.json`. Для Завойко основание приоритета — перекрёсток с пешеходным переходом.

Карточка ищет последний сопоставимый кадр до ухудшения за сутки с той же камеры. После выезда оператор может просмотреть и закрепить свежий кадр после работ. Отметки «Подтвердилось», «Ложный сигнал» и «Уже в работе» сохраняются отдельно от решения и видны в сводках.

### Проверочная почта

Для локального `preview` доступен изолированный почтовый приёмник:

```bash
docker compose -f compose.yaml -f compose.s3.yaml -f compose.mail-test.yaml build api
docker compose -f compose.yaml -f compose.s3.yaml -f compose.mail-test.yaml up -d --no-build
```

[Почтовый ящик Mailpit](http://127.0.0.1:8025) принимает письма на тестовый адрес `dispatch@example.test`. Реальные получатели настраиваются через `MAIL_TO` и TLS SMTP в режиме `live`. Форматы доставки включают прогнозное предупреждение, оперативный сигнал с JPEG и утреннюю сводку. Демо хранит сообщения в своём журнале.
